# VroksNet.Infrastructure

Project-level rules. Solution-wide rules (dependency direction, coding rules) are in `.claude/CLAUDE.md`.

- `src/VroksNet.Infrastructure` — Clean Architecture Infrastructure layer. References `VroksNet.Application`.
- **Infrastructure** — implementations of Application's interfaces: persistence (EF Core, repositories), external service clients, file system, email, etc. Depends on Application (and transitively Domain).

## Notes

- **Persistence: SQLite via EF Core, one `DbContext`, all writes serialized.** `VroksNet.Infrastructure.Persistence.VroksNetDbContext`, resolved through `IDbContextFactory<VroksNetDbContext>` (not injected directly) so every read/write gets its own short-lived context. Writes never go straight to the context — call sites (e.g. `ApiSpecificationRepository`) enqueue a delegate through `IDbWriteQueue`, and the single `DbWriteBackgroundService` consumer executes them one at a time. This is deliberate (see `docs/project-brief.md` section 3 on the concurrent-write risk between the Mock API and the async publish worker) — don't add a second write path that bypasses the queue. WAL journal mode and a 5s busy_timeout are applied in `InfrastructureServiceCollectionExtensions` — `AddInfrastructure(...)` for the connection setup, `InitializeDatabaseAsync()` (called once at ApiService startup) for migrations + the `PRAGMA journal_mode=WAL` statement.
  - **Defaults to an in-memory SQLite database** (`Data Source=VroksNetInMemoryDb;Mode=Memory;Cache=Shared` — named + shared-cache, not bare `:memory:`, since `:memory:` would give every `IDbContextFactory`-issued connection its own private empty database) when `ConnectionStrings:VroksNetDb` isn't configured — nothing to clean up locally, fresh state every process start. `InMemoryDatabaseKeepAlive` (a singleton, resolved eagerly at the top of `InitializeDatabaseAsync` before migrations run) holds one connection open for the app's lifetime; without it the shared-cache database would be dropped the instant the first short-lived `IDbContextFactory` connection closes. Set `ConnectionStrings:VroksNetDb` (config, `ConnectionStrings__VroksNetDb` env var, or user secrets) to a real file path to persist across restarts instead — this is the "parameter" that switches modes, not a separate flag.
  - **Docker already opts into the persistent, file-backed mode** — the image sets `ConnectionStrings__VroksNetDb=Data Source=/app/data/vroksnet.db` and declares `VOLUME /app/data` (see `Dockerfile`), so a container's data survives being recreated. Local `dotnet run` (no override) gets the in-memory default instead.
  - **In file mode, `AddInfrastructure` creates the configured path's parent directory if it's missing** (`Directory.CreateDirectory` on `SqliteConnectionStringBuilder.DataSource`'s directory portion) — SQLite itself already creates the `.db` file on first connect (default `ReadWriteCreate` mode) but never creates missing parent directories, which would otherwise fail on a fresh volume or a nested path a user types into the Settings page's storage helper (see below).
  - **The Settings page (`Storage` section) only helps construct the `ConnectionStrings__VroksNetDb` value and copies it to the clipboard — it never changes the running app's own connection.** There is no live "switch to persistent storage" toggle: `IDbContextFactory` is wired once at startup in `AddInfrastructure`, so switching modes always means setting that env var (or config key) and restarting the process — something this app cannot safely trigger on itself (no supervisor to guarantee it comes back up outside a Docker restart policy). Keep it that way; don't add a "restart now" button without that guarantee in place.
- **Spec replace semantics**: `ApiSpecificationRepository.UpsertAsync` deletes any existing row with the same `Title` (cascades to its `MockEndpoint`s) and inserts fresh, rather than attaching/patching a detached graph — that path threw `DbUpdateConcurrencyException` when tried. `Title` has a unique index (`VroksNetDbContext.OnModelCreating`); don't relax it without revisiting this.
- **Migrations**: run from the repo root — `dotnet ef migrations add <Name> --project src/VroksNet.Infrastructure --startup-project src/VroksNet.ApiService --output-dir Persistence/Migrations`. `Microsoft.EntityFrameworkCore.Design` has to be referenced by **both** projects (Infrastructure for the model, ApiService because `dotnet ef` requires it on whatever `--startup-project` is) — the tools give a clear error if either is missing.
- **OpenAPI parsing**: `Microsoft.OpenApi` + `Microsoft.OpenApi.YamlReader` (3.x line). The YAML reader isn't auto-registered — call `new OpenApiReaderSettings().AddYamlReader()` (extension in `Microsoft.OpenApi.Reader`) and pass those settings into `OpenApiDocument.LoadAsync(stream, "yaml", settings, cancellationToken)`, or you'll hit `NotSupportedException: Format 'yaml' is not supported.`
- **AsyncAPI parsing** (`AsyncApiSpecificationParser`): there's no AsyncAPI counterpart to `Microsoft.OpenApi`'s typed object model on NuGet, so it walks the raw YAML tree via `SharpYaml`'s representation model (`YamlMappingNode`/`YamlSequenceNode`/`YamlScalarNode`) and resolves the spec's own local `"#/a/b/c"` `$ref`s by hand — deliberately minimal, this spec's own refs only, not a general JSON Reference/external-file implementation. `SharpYaml` is referenced directly in `VroksNet.Infrastructure.csproj` rather than added as a second general-purpose YAML library: it's already pulled in transitively by `Microsoft.OpenApi.YamlReader` (pin it to the exact version that package brings — `2.1.5` as of writing — so it can't silently drift out of sync with that transitive edge). Operation keys follow `MockEndpoint.OperationKey`'s documented AsyncAPI convention, `"{channel address}:{action}"` (e.g. `"orders.created:send"`) — these are **not** invokable through `/mock/{**path}` (`MockInvocationEndpoints`/`OperationKeyMatcher` assume HTTP method+path semantics); actually publishing them is the Phase 03 async-mock publish worker, not built yet (see docs/project-brief.md section 2, and the "Message brokers" bullet in `src/VroksNet.AppHost/CLAUDE.md`).
- **Two parser interfaces, not one shared one.** `ISpecificationParser` (→ `OpenApiSpecificationParser`) and `IAsyncApiSpecificationParser : ISpecificationParser` (→ `AsyncApiSpecificationParser`) are registered side by side in `AddInfrastructure`. `IAsyncApiSpecificationParser` adds no members of its own — it exists purely so DI can tell the two registrations apart; each kind's import handler (`ImportOpenApiSpecHandler` / `ImportAsyncApiSpecHandler`) asks for its own kind by type instead of both racing for the same unqualified `ISpecificationParser` registration (last registration would silently win). The two kinds stay fully separate vertical slices end to end — own `Application/Specifications/Import{Kind}Spec` request+handler, own `POST /api/specifications/{openapi|asyncapi}` endpoint — rather than one handler branching on a `Kind` parameter; follow that pattern if a third spec kind shows up.
- **Connection testing** (`IConnectionTester` → `ConnectionTester`, `POST /api/connections/{id}/test`): actually reaches a stored `Connection`'s target rather than just validating shape. This is deliberately **not** the same client path `AddRabbitMQClient("rabbitmq")`/`AddNatsClient("nats")` use (see `src/VroksNet.AppHost/CLAUDE.md`, "Message brokers") — those are Aspire-wired to the dev-time broker resources in `AppHost.cs`; a `Connection` holds an arbitrary user-typed host/credentials that has nothing to do with those, so `ConnectionTester` opens its own client directly: a short-timeout `HttpClient` GET for `Http` (any HTTP response counts as reachable, even a 4xx — only a thrown exception counts as failure), `RabbitMQ.Client`'s `ConnectionFactory.CreateConnectionAsync` for `RabbitMq`, and `NATS.Client.Core`'s `NatsConnection.PingAsync` for `Nats` — both referenced directly in `VroksNet.Infrastructure.csproj` (not the `NATS.Net`/`Aspire.NATS.Net` meta-packages, which pull in JetStream/KV/ObjectStore/Hosting nothing here needs) and pinned to the exact versions those two Aspire client packages themselves already resolve, so the direct reference can't drift out of sync with what's already in the graph. All three branches share one 5s timeout and return `ConnectionTestResult(bool Success, string Message)` — `Message` is written to be safe to show verbatim in the UI (never a raw connection string or full stack trace).
- **Contract-testing schema foundation** (`ISchemaValidator` → `VroksNet.Infrastructure.SchemaValidation.SchemaValidator`, `MockEndpoint.RequestSchema`/`ResponseSchema`): full plan and rationale in `docs/contract-testing-plan.md` — this bullet is just the pointer. Validates a JSON instance against a JSON Schema via `JsonSchema.Net` (pinned in `Directory.Packages.props`, the only place that library is referenced). `OpenApiSpecificationParser`/`AsyncApiSpecificationParser` now also extract each operation's request/response (or, for AsyncAPI, message payload — reuses `ResponseSchemaJson` rather than adding a third field) schema, self-contained (local `$ref`s inlined via `IOpenApiSchema.SerializeAsV31(...)` with `OpenApiWriterSettings { InlineLocalReferences = true }` for OpenAPI, one manual `$ref` hop for AsyncAPI) — stored on `MockEndpoint` at import time rather than re-parsed on demand, same reasoning as `ExampleTemplate` already storing the example instead of re-reading `ApiSpecification.RawContent` each time. **Nothing consumes these yet** — no behavior changes, they're not even exposed through `MockEndpointDetail`/the API/the UI. This is deliberately just the foundation Phase (contract-testing-plan.md "Фаза A"); don't wire up validation against them without also updating that plan.
