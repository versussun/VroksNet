# VroksNet.E2ETests

Playwright browser E2E tests: boots the same real `AppHost` graph as `VroksNet.IntegrationTests` (same one-shared-boot-per-run, same container-runtime requirement, same fresh-in-memory-database and GUID-suffix points — see `tests/VroksNet.IntegrationTests/CLAUDE.md`), then drives `webfrontend` through an actual Chromium instance rather than calling the API directly — this is the layer that would catch a Blazor component wired up wrong even though the API underneath is fine. Shared xUnit rules are in `tests/CLAUDE.md`.

- `Fixtures/AppHostFixture.cs` additionally launches **one shared Playwright `IBrowser`** in the same `InitializeAsync` (also too slow to redo per test) and exposes `WebBaseAddress` (`App.GetEndpoint("webfrontend")`) for tests to navigate against. Headless by default; run with `HEADED=1` locally to watch a test execute while debugging it.
- `Fixtures/PageTestBase.cs` is the per-test-class base every test class extends: since xUnit constructs a fresh test-class instance per test method, its `IAsyncLifetime.InitializeAsync`/`DisposeAsync` opening/closing a fresh `IBrowserContext`/`IPage` there gives each test its own cookies/local-storage isolation for free, while still reusing the one shared browser process.
- **Playwright's browser binaries must be installed once** before these tests can run — build the project, then run the generated `bin/Debug/net10.0/playwright.ps1 install` (add `--with-deps` on a fresh Linux CI box). Not needed again until the pinned `Microsoft.Playwright` version (`Directory.Packages.props`) changes.
- Prefer `Page.GetByRole`/`GetByLabel`/`GetByText` locators over CSS selectors — they're what make a Razor component's markup need real `<label for>`/ARIA-role structure to be testable at all, which is worth fixing in the component if missing (see `Settings.razor`'s `for`/`id` pairs, added specifically so `GetByLabel` could find its inputs) rather than reaching for a brittle CSS locator instead.
- **`webfrontend`'s WASM app cannot actually reach `apiservice` under `DistributedApplicationTestingBuilder` without a fixup — confirmed by running this whole suite against real Docker for the first time.** `Web/wwwroot/appsettings.Development.json` hardcodes `ApiService:BaseAddress` to `https://localhost:7352`, which only means something for a *real* `dotnet run` AppHost process — its DCP proxy is what makes that pinned port actually forward to `apiservice`'s real (random) port (see the "Dev-time ports" bullet in `src/VroksNet.AppHost/CLAUDE.md`). Under the **testing** builder this project's fixtures use, that proxying doesn't happen: `Get-NetTCPConnection` during a live test run showed nothing ever listening on 7352 — `apiservice` just gets a genuine random port like every other resource here. Every `fetch()` the WASM app made therefore failed with a bare `net::ERR_CONNECTION_REFUSED` (`Page.RequestFailed`/browser console showed this precisely; the on-page error was only ever the unhelpful generic `TypeError: Failed to fetch`) — this silently broke every E2E test that adds/uploads something (create-then-see-it-in-the-list), while pure-navigation tests (`HomeNavigationTests`) kept passing, which is what made it easy to miss.
  - **Fix in place**: `AppHostFixture.InitializeAsync`, after `App.StartAsync()`, resolves `apiservice`'s *actual* endpoint via `App.GetEndpoint("apiservice", "https")` and overwrites `wwwroot/appsettings.Development.json` in place with it, restoring the original content in `DisposeAsync`. Every test in the collection shares the one `AppHostFixture` instance, so this happens exactly once per run, before any test navigates.
  - **Why not point it at a different `appsettings.{Environment}.json` instead** (cleaner — never touching a checked-in file, even temporarily)? Tried first, doesn't work: standalone Blazor WebAssembly's environment name became a **build-time-only** MSBuild property (`WasmApplicationEnvironmentName`) as of .NET 10 — setting `ASPNETCORE_ENVIRONMENT` on the dev-server *process* (`.WithEnvironment(...)` on the `webfrontend` resource, which controlled this in .NET 8/9) is no longer read at runtime at all. Confirmed by testing that approach directly and observing zero effect before finding the real cause.
